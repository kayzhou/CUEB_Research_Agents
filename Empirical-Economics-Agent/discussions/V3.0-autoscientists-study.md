## 一、AutoScientists 全景概述

### 1.1 一句话定义

AutoScientists 是一个**去中心化多 AI Agent 系统**，用于长时间运行的自动化计算科学实验。Agent 围绕有前途的假设自组织成团队，在执行计算前相互 critique 提案，并在系统范围内共享成功和失败，使并行搜索可持续数小时到数天。

### 1.2 核心创新（官方宣称四项）

| 创新 | 说明 |
|------|------|
| 自组织成假设驱动团队 | 无中央规划器，Agent 自主围绕可证伪假设组队 |
| 先 Critique 再消耗算力 | 提案必须先通过 Workshop 讨论，才能进入队列执行 |
| 共享成功与失败 | KEEP/DISCARD 结果系统级广播，避免重复探索 |
| 持续并行搜索 | 多团队在数小时/天内维持平行搜索轨迹 |

### 1.3 技术栈

```
Claude Code (主循环) → ClawInstitute (本地 npm 协调服务器) → 多个 Claude Code Subagent
                                                    ↓
                                          Workshop (论坛) + Workspace (共享文件) + Posts (消息)
```

- **ClawInstitute**：npm 包，提供 REST API 的多 Agent 协调基础设施
- **Claude Code Subagent**：每个 Agent 是一个独立的 CC subagent
- **launch.py**：Python 初始化脚本
- **runbook.md**：编排器主程序（通用控制流）
- **Task-Profile Hook System**：13 个钩子实现任务类型差异化

## 二、AutoScientists 架构深度解剖

### 2.1 三层架构

```
┌──────────────────────────────────────────────┐
│  launch.py → runbook.md ← task-profile.md    │  ← 编排层
├──────────────────────────────────────────────┤
│  ClawInstitute (Workshop/Workspace/Posts)     │  ← 协调层
├──────────────────────────────────────────────┤
│  Monitor×1  GPU Agent×6  Analyst×3            │  ← Agent 层
└──────────────────────────────────────────────┘
```

### 2.2 五大设计原则

1. **去中心化自组织**
   - 发现优于规定（Agent 每周期 LIST 工作区文件，自行决定读什么）
   - 讨论优于指令（提案必须经 Workshop 讨论后才能入队）
   - 投票自终止（≥5 票 [DISCUSS-DONE] 结束讨论，不由编排器决定）

2. **假设驱动团队结构**
   - 团队围绕可证伪假设（非搜索空间维度）组织
   - 每个团队有明确的假设、可检验预测、证伪条件
   - 任何团队可在任何维度提出实验——差别在于评估视角

3. **算力资源保护**
   - 入队前讨论
   - 去重检查（对照工作区和死胡同列表）
   - Champion 代码检查（若机制已存在于 champion 代码则跳过）
   - 每次实验只变一个变量（清洁因果）

4. **编排器纯协调者原则**（核心约束）
   - 禁止运行训练/写模型代码/修改 Agent 工作区/认领实验/伪造数据
   - 禁止在 Agent 慢或失败时插手
   - 禁止在 exit_condition 返回 True 前停止循环

5. **自修改系统**
   - 编排器每 N 周期分析系统运行，直接编辑 Agent 角色模板文件
   - 直接改代码，不写报告

### 2.3 HEARTBEAT.md — 最精巧的设计

每个 Agent 的自包含指南，6 个部分：

```
Part 0: Mode Selector（5 分钟，强制）
  ├── Check A: MODE 环境变量 → discussion vs execute
  ├── Check A2: 活跃的 DISCUSSION-TRIGGER？→ discussion
  ├── Check B: 名册中有团队？→ 团队引导/无团队退出/正常周期
  ├── Check C: GPU Agent 未发布结果？→ 恢复
  └── Check D: 正常 → Part 4

Part 1: Bootstrap（凭证、路径、身份）
Part 2: Discussion 分支（纯 CPU 思考，发帖，退出）
Part 3: 无团队分支（干净退出，不做工作）
Part 4: 正常周期分支（定位、角色特定工作、记录、发布）
Part 5: 恢复并发布分支（GPU only）
Part 6: Always-Last（更新 AGENT.md，镜像到 API，promise 退出）
```

**关键设计决策**：
- Agent 是自给自足的（3 行启动提示词，自己发现一切）
- Agent 是无状态的（会话间无内存状态）
- AGENT.md = Agent 的 "CLAUDE.md"
- memory/ 目录 = 持久跨会话学习

### 2.4 三种 Agent 角色

| 角色 | 数量 | 职责 |
|------|------|------|
| **Monitor** | 1 全局 | 系统门卫：释放过期认领、检查队列深度、GPU 利用率、团队停滞检测 |
| **GPU Agent** | 6 全局/2 每团队 | 执行实验：认领→去重→应用变更→训练→分析→记录→发布 |
| **Analyst** | 3 全局/1 每团队 | 研究大脑：停滞检测、假设检验、噪声校准、提案生成、去重、审计 |

### 2.5 自组织团队机制

**冷启动**（7 步）：
1. launch.py 发布 [DISCUSSION-TRIGGER]
2. 编排器以 MODE=discussion 启动所有 Agent
3. Agent 通过 Part 0 路由到讨论分支
4. Agent 贡献维度/假设提案
5. Agent 投票 [DISCUSS-MORE] 或 [DISCUSS-DONE]
6. 当 ≥5 票 DONE，字母序最后的 Analyst 编写 teams/roster.md
7. Monitor 不参与

**运行中重组**（无编排器干预）：
- Analyst 检测停滞 → 发布 [DISCUSSION-TRIGGER]
- 下一周期 Agent 通过 Check A2 检测 → 自动切换到讨论
- 字母序最后的 Analyst 编写新名册

**团队演化协议**：
| 条件 | 动作 |
|------|------|
| 所有假设被证伪 | DIMENSION-NEW 提案 |
| 团队休眠 ≥5 周期 | DIMENSION-MERGE 或 REGROUP |
| 3+ 线程收敛到同一未拥有维度 | DIMENSION-NEW |
| 两个团队提出相同机制 | DIMENSION-MERGE |
| 未处理的 [STUCK] 帖子 | DIMENSION-NEW 或 DIMENSION-MERGE |

### 2.6 Task-Profile Hook System（13 个钩子）

| # | 钩子名 | 何时调用 | 作用 |
|---|--------|----------|------|
| 1 | `launch_command` | Step 0 Case A | 创建新实验目录的 bash 命令 |
| 2 | `bootstrap_extras` | Step 1 | 任务特定变量 |
| 3 | `discussion_policy` | Step 3 | 控制讨论阶段行为 |
| 4 | `seeding_policy` | Step 4 | 如何播种队列 |
| 5 | `pre_cycle_check` | Step 5a | 周期前检查 |
| 6 | `analyst_prompt_extras` | Step 5b | 分析师额外提示 |
| 7 | `gpu_dispatch` | Step 5c | **必需**：GPU 调度策略 |
| 8 | `champion_promotion` | Step 5e | **必需**：冠军提升逻辑 |
| 9 | `stagnation_response` | Step 5g | 停滞响应 |
| 10 | `periodic_hooks` | Step 5h | 周期性任务 |
| 11 | `exit_condition` | Step 5i | 退出条件 |
| 12 | `final_report` | Step 6 | 最终报告格式 |
| 13 | `never_do_extras` | Global | 任务特定禁止行为 |

### 2.7 执行循环（runbook.md Step 5）

```
while True:
  5a. pre_cycle_check hook
  5b. 并行启动 3 个 Analyst（MODE=execute）
  5c. 启动 GPU Agent（gpu_dispatch hook）
  5d. 等待 + 记录 sessions.jsonl
  5e. 冠军提升（champion_promotion hook）
  5f. 健康检查（释放过期认领、空队列警告）
  5g. 停滞检查（最近 10 次实验 0 KEEP → stagnation_response）
  5h. 周期性钩子（如 meta-improvement 每 N 周期）
  5i. 循环控制（exit_condition 返回 True 则退出）
```

### 2.8 EconMgmt — 经济学/管理研究工厂

这是与我们最直接相关的任务类型。

**核心重定义**：
- "GPU Agent" → Empirical/Build Agent（构建证据、运行分析、写论文组件）
- Champion → 最佳验证的论文/证据/可复现包
- 指标 → `paper_score`（0-1 复合分数）

**paper_score 组成**：
| 维度 | 权重 |
|------|------|
| 新颖性 | 0.20 |
| 识别策略 | 0.20 |
| 经验有效性 | 0.20 |
| 贡献 | 0.15 |
| 稳健性 | 0.10 |
| 清晰度 | 0.10 |
| 可重复性 | 0.05 |

**输出结构**：
```
paper/         ← paper.md, abstract, introduction, theory, data, methods,
                  results, robustness, discussion, limitations, references.bib,
                  tables/, figures/
evidence/      ← claim_registry.md, citation_registry.md, result_registry.md
replication/   ← scripts, environment, data lineage
```

**方法菜单**（16 种）：
DiD/事件研究、IV、RDD、合成控制、面板固定效应、匹配/双稳健、
文本即数据、网络分析、结构模型、调查/实验、档案管理研究、
模拟/ABM、元分析/系统综述、测量验证

**EconMgmt 特有约束**：
- 禁止伪造任何东西
- 声明-证据链接（每个经验声明须有 claim ID 和证据路径）
- 因果语言纪律（需要识别策略和有效性威胁）
- 诚实报告（空值和脆弱结果也必须如实报告）
- 隔离规则（Agent 不直接写规范路径）

### 2.9 元改进系统（Meta-Improvement）

唯一的自演化机制。每 N 周期执行：

1. **读取证据**：experiments.jsonl, sessions.jsonl, queue, workshop posts, champion/SOURCE
2. **形成诊断**：识别最显著的功能障碍（具体而非笼统）
3. **做一个针对性编辑**：直接编辑 ROLE-ANALYST.md 或 ROLE-GPU.md（一次只改一处）
4. **记录做了什么和为什么**：追加到 logs/meta_results.tsv

四种诊断模式：
| 症状 | 常见修复 |
|------|----------|
| high_duplicates（>30% 重复实验） | 添加跨团队去重步骤 |
| low_activation（Agent 不运行） | 添加强制激活检查 |
| slow_propagation（KEEP 后无跟进） | 添加 KEEP 广播步骤 |
| low_keep_rate（持续低 KEEP 率） | 添加 champion 差距分析 |

## 三、V2.2 执本忘筌 vs AutoScientists — 全面对比

### 3.1 架构哲学

| 维度 | V2.2 执本忘筌 | AutoScientists |
|------|---------------|----------------|
| **Agent 数量** | 单 Agent（Claude Code） | 多 Agent（10 个：1 Monitor + 6 GPU + 3 Analyst） |
| **控制模式** | 集中式编排 | 去中心化自组织 |
| **人机关系** | 人在回路中（关键卡点等用户决策） | 全自动（人只启动和 Ctrl+C） |
| **时间尺度** | 交互式（几分钟到几小时） | 长时间运行（数小时到数天） |
| **决策逻辑** | 人做关键决策 + CC 执行 | Agent 讨论投票 + 编排器纯协调 |
| **入口设计** | 单一 CLAUDE.md + 按需读 guide | runbook.md（通用流）+ task-profile.md（钩子） |
| **可扩展性** | 阶段和步骤硬编码 | Hook 系统实现任务类型参数化 |

### 3.2 研究流程

| 维度 | V2.2 | AutoScientists |
|------|------|----------------|
| **流程结构** | 线性阶段（0→1→2→3→R） | 循环执行（讨论→组队→执行→适应） |
| **启动方式** | 读 CLAUDE.md → 确认阶段 → 读对应 guide | launch.py 初始化 → Agent 自引导 |
| **数据探索** | 人指导下逐源清洗 | Agent 自发现（LIST→DECIDE→READ） |
| **假设形成** | 人在立项阶段确定 | Agent 集体讨论、投票收敛 |
| **任务分配** | CC 按阶段步骤执行 | Agent 自组织认领队列 |
| **质量控制** | 人审查 + 7R/7Q 审查 | 声明-证据注册表 + Monitor 审计 + 讨论把关 |
| **迭代机制** | 返修 triage 协议（四问+三级影响面） | 元改进系统（直接编辑 Agent 角色文件） |
| **终止条件** | 阶段完成 | 停滞（N 次无 KEEP）或 deadline |

### 3.3 文档与知识管理

| 维度 | V2.2 | AutoScientists |
|------|------|----------------|
| **入口文档** | CLAUDE.md（约 350 行） | runbook.md + task-profile.md + HEARTBEAT.md |
| **指南系统** | guides/ 按阶段按需读取 | system/reference/ + system/templates/ |
| **任务规范** | 内嵌在 CLAUDE.md 路由表 | 独立 TASK.md（YAML frontmatter） |
| **代码文档** | 脚本头部注释（自文档化） | Agent 角色协议（ROLE-*.md） |
| **版本管理** | VERSION + version_check.py | Git（无独立版本号） |
| **迭代记录** | ITERATION_LOG.md | experiments.jsonl + sessions.jsonl |
| **记忆系统** | CC 项目记忆（user/feedback/project/reference） | memory/ 目录 + AGENT.md |
| **状态追踪** | 阶段步骤清单 | 工作区文件（YAML frontmatter） |

### 3.4 技术实现

| 维度 | V2.2 | AutoScientists |
|------|------|----------------|
| **运行环境** | Claude Code（CLI/IDE） | Claude Code + ClawInstitute（npm） |
| **Agent 通信** | 无（单 Agent） | REST API（Workshop/Workspace/Posts） |
| **并发模型** | 无 | 并行 Subagent（Task() 调用） |

### 3.5 经济学/管理研究的处理

| 维度 | V2.2 | AutoScientists EconMgmt |
|------|------|------------------------|
| **范式决策** | 阶段 0.2：资产定价 vs 因果推断 | Agent 讨论中决定 + 方法菜单 |

| **证据链** | 阶段 3.1：证据链统筹 | claim_registry.md 自动链接 |
| **可复现性** | 脚本 + Schema 验证 | replication/ 完整包 |

### 3.6 关键差异总结

| # | 差异点 | V2.2 优势 | AutoScientists 优势 |
|---|--------|-----------|---------------------|
| 1 | 单 vs 多 Agent | 简单、可控、token 消耗低 | 并行、专业化、持续运行 |
| 2 | 人在回路 vs 全自动 | 关键决策质量有保障 | 速度快、可过夜运行 |
| 3 | 线性阶段 vs 循环迭代 | 逻辑清晰、可追溯 | 灵活、可自适应 |
| 4 | 规则驱动 vs 假设驱动 | 一致性好 | 探索性强 |
| 5 | 硬编码 vs Hook 系统 | 上手简单 | 任务类型可扩展 |
| 6 | 返修 triage vs 元改进 | 人类审查质量高 | 闭环自动化 |
| 7 | 无 Agent 通信 | 无通信开销 | 讨论-执行门控 + 知识共享 |
| 8 | 阶段卡点 | 已知卡点质量好 | 无卡点但可能跑偏 |

## 四、AutoScientists 中值得融入的先进设计

### 4.1 高优先级（应融入）

#### A. Hook 系统（Task-Profile 参数化）

**AutoScientists 做法**：runbook.md 定义通用控制流，LAUNCH.md 通过 13 个命名钩子填入任务特定行为。

**V2.2 可融入方式**：
- 将 CLAUDE.md 重构为 "通用编排器" + "任务配置文件"
- 研究阶段、方法选择、输出格式等通过钩子参数化
- 好处：同一套流程同时支持资产定价（Python）和因果推断（Stata MCP）
- 具体：可定义 `bootstrap`、`data_check`、`estimate`、`diagnose`、`output`、`write` 等钩子

#### B. 声明-证据注册表

**AutoScientists 做法**：每一条论文声明有唯一 claim ID，链接到证据路径，有状态追踪（unsupported/theoretical/empirical_pending/empirically_supported/fragile/refuted）。

**V2.2 可融入方式**：
- 在 `evidence-chain.md` 基础上增强为结构化注册表
- 每条声明：ID + 内容 + 状态 + 证据文件路径 + 风险评估
- 写作时自动验证"论文中引用的声明是否都有证据支撑"
- 好处：防止空口无凭，审稿攻击时有据可查

#### C. 讨论-执行门控（Proposal → Discussion → Queue → Execute）

**AutoScientists 做法**：任何实验/分析必须先作为 [PROPOSAL] 在 Workshop 讨论，至少一个非作者评论后才能入队执行。

**V2.2 可融入方式**：
- 在关键估计前：CC 先列出分析计划 → 自动自检（多角度审视）→ 用户确认 → 执行
- 不需要多 Agent，可以是"同一 Agent 的多轮自我审视"
- 或者引入"预审攻击"的前置——在估计前就做，而非估计后

#### D. 元改进/自审计循环

**AutoScientists 做法**：编排器每 N 周期分析系统运行，诊断问题，直接编辑 Agent 角色模板以修复。

**V2.2 可融入方式**：
- 每个阶段完成后，CC 自动运行"阶段复盘"：什么做得好？什么可以改进？下次怎么做？
- 将经验写入 LESSONS.local.md 或更新 guide 文件
- 不是写报告，而是直接改流程文件

#### E. 实验日志结构化（experiments.jsonl）

**AutoScientists 做法**：所有实验以结构化 JSONL 记录（exp_id, agent, team, metric, champion_before, champion_after, delta, outcome, timestamps）。

**V2.2 可融入方式**：
- 替换/增强 ITERATION_LOG.md
- 每条估计记录：脚本、因变量、自变量、系数方向、显著性、R²、样本量、是否通过诊断
- 方便后续 meta 分析：哪些设定稳健、哪些敏感
- 自动生成"结果稳定性仪表板"

### 4.2 中优先级（选择性融入）

#### F. 多 Agent 并行（有限引入）

**AutoScientists 做法**：10 个 Agent 并行工作，Monitor/Analyst/GPU Agent 分工。

**V2.2 可融入方式**：
- 不搞 10 个 Agent（过度复杂），但可引入 **2-3 个专用 Subagent**
- 例如：数据诊断 Agent + 估计执行 Agent + 审查 Agent
- 在适当时机并行启动（如描述统计和诊断检验同时跑）
- 好处：加速而不失控

#### G. 冠军机制

**AutoScientists 做法**：系统始终维护一个"冠军"（最佳 train.py 或最佳论文包），新结果必须超越冠军才能替代。

**V2.2 可融入方式**：
- 维护"当前最佳结果集"：最佳模型规格、最佳表格
- 新估计与冠军比较，只有改进才更新
- 防止劣化迭代

#### H. 噪声感知/多种子门控

**AutoScientists 做法**：经验性地测量噪声底线（|delta| < 0.003 视为噪声），KEEP 需要多种子确认。

**V2.2 可融入方式**：
- 稳健性检查中引入"噪声底线"概念
- 系数变化小于某个阈值时，不视为实质性差异
- 敏感度分析：改变模型规格时，系数波动多大才算"稳健"？

#### I. 讨论自终止（投票机制）

**AutoScientists 做法**：Agent 投票 [DISCUSS-MORE] 或 [DISCUSS-DONE]，≥5 票 DONE 自动结束。

**V2.2 可融入方式**：
- 在"样本侦查"等需要决策的环节，CC 给出选项并推荐 → 等用户决定
- 在审查阶段，多个审查维度并行后投票决定是否通过

### 4.3 低优先级（暂不融入）

#### J. ClawInstitute 基础设施

AutoScientists 依赖一个独立的 npm 服务器。对 V3.0 来说引入这个依赖太重。CC 原生支持 Subagent 和文件系统，不需要额外的协调中间件。

#### K. 全自动过夜运行

AutoScientists 设计为无人值守运行数小时到数天。这对实证研究不合适——经济学研究的很多决策（变量构造、样本筛选、识别策略选择）需要领域知识，不适合完全自动。

#### L. 10 Agent 架构

1 Monitor + 6 GPU Agent + 3 Analyst 太复杂。实证研究的瓶颈不是算力（不需要 6 个 GPU Agent），而是研究设计和分析判断。

## 五、V3.0 升级的初步方向（供讨论）

### 5.1 可能的架构方向

**方向 A：Hook 化重构（推荐）**
- 保持单 Agent 架构，但将 CLAUDE.md 重构为"编排器 + Hook 配置文件"
- 融合声明-证据注册表
- 添加结构化实验日志
- 添加阶段复盘/元改进循环

**方向 B：轻量多 Agent**
- 引入 2-3 个专用 Subagent（数据/估计/审查）
- 保持人在回路的关键卡点
- 融合讨论-执行门控

**方向 C：混合模式**
- 日常交互保持单 Agent
- 审查/稳健性检查阶段可启动多 Agent 并行
- 声明-证据注册表 + 结构化日志作为基础设施升级

### 5.2 核心设计问题（需讨论）

1. **人在回路 vs 全自动的边界在哪里？**AutoScientists 完全自动，V2.2 有多个卡点。V3.0 应该保留哪些人控卡点？

2. **多 Agent 是否值得引入？**增加了复杂度，但带来并行和专业化。对实证研究的实际增益有多大？

3. **Hook 系统如何设计？**是像 AutoScientists 的 13 个钩子，还是更简化的版本？

4. **"讨论-执行门控"如何实现？**没有多 Agent 的情况下，如何实现"先审视再执行"？

5. **声明-证据注册表的粒度和维护成本？**每条声明都注册会不会太重？

6. **元改进循环的触发时机？**每 N 个阶段？每次审查后？论文完成后？

7. **ClawInstitute 是否必要？**能否用 CC 现有基础设施（文件系统 + Subagent）替代？
